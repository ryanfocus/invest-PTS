# 08: 出場程式（13:25）

**What to build:** 一支獨立的出場程式，13:25 由排程叫醒，單獨負責 PTS 的出場。交易微台時，平掉 PTS 自己的全部口數；交易大台、小台時不送單，交給券商 13:30 當沖強平。任何不確定的情況都不猜，改發 Discord 請使用者處理。

**Blocked by:** 06

**Status:** ready-for-agent

- [x] 盤中程式沒在跑、或當天當掉，出場程式照常執行（規格第 49 條）。
- [x] 非交易日完全安靜（規格第 40 條）。
- [x] 交易商品以部位檔記載的為準，不看設定檔（規格第 43 條）。
- [x] 微台：市價平掉 PTS 自己的全部口數，只平 PTS 開的口數；超過 10 口拆成多筆（規格第 31、32、33 條）。
- [x] 大台、小台：不送任何出場單，結算日也一樣，由交易所以最後結算價了結（規格第 30、35 條）。
- [x] 平倉單沒送出去：每分鐘重試、最多 3 次；只成交一部分：剩下的口數照同樣方式重試；最後仍有剩餘就告警，寫明還剩幾口（規格第 34 條）。
- [x] 出場單送出去但不知道成交：絕不重送。改用該單的委託序號做兩段查詢（委託紀錄取得委託書號、成交紀錄加總口數）。查到全部成交就視為已平倉，不告警；只成交一部分、查不到、查詢失敗都告警，並附上查到的口數（規格第 50 條後半）。
- [x] 部位為「不確定」：不送單，告警（規格第 50 條）。
- [x] 部位檔讀不懂：不送單，告警（規格第 38 條）。
- [x] 13:45 之後才補跑：不送單，告警請使用者在夜盤自行處理（規格第 55 條）。
- [x] 平倉完成後，部位檔標記為已了結。
- [x] 測試涵蓋以上每一種情境，斷言送出的委託、發出的訊息、部位檔內容。

## Comments

**2026-11-10（實作者）：這張沒有標「實機」的驗收條件，全部以測試完成**（`tests/test_exit_program.py`
從 `exit_program.run` 打進去，斷言送出的委託、發出的訊息、部位檔內容；`tests/test_fill_query.py`
測兩段查詢的線路格式與群益 broker）。實作者依規定不連真實券商，下面幾件事**待實機驗證**（併入 ticket 11）：

1. **兩段查詢在 PTS 還沒真的跑過。** 解析與欄位位置搬自 invest-os，用它的真實微台單腳樣本驗證
   （`tests/fixtures/reports-*.txt`）。出場只會平微台、微台不標當沖，所以查詢只會碰到已驗證過的那種列；
   但 `CapitalBroker.query_fills` 本身（含兩段之間等 5.5 秒）第一次執行會在實機上。
2. **回報連線斷了時，委託查詢與成交查詢還查不查得到。** 查詢刻意不經過「回報連線斷了就不送」
   那道檢查（平倉單沒回報，最常見的原因就是回報斷線），假設它們走下單元件的阻塞式呼叫、不靠回報
   連線。文件沒有寫明，第一次遇到時看 log。
3. **結算日的微台 13:30 停止交易。** 依期交所規則（近月最後交易日 08:45～13:30），結算日 13:30 之後
   出場程式不送單，還在的口數由交易所以最後結算價了結。只有規則、沒有實機樣本——所以照樣告警
   「部位還在」，請使用者結算後確認帳戶（審查後修正，原本不告警）。

**實作上的決定（規格沒有逐字寫到的地方）：**

- 進入點 `python exit_program.py`；`exit_program.run(broker, config, *, notify, clock, sleep)`。
  出場程式啟動時讀一次時鐘，重試前等一分鐘、等完再看一次時鐘（兩者都由參數注入）。
- **已了結 = 出場明細的口數等於進場**（`PositionRecord.open_lots == 0`），不另存旗標，部位檔格式沒變。
  出場程式只平 `open_lots`，所以中途被關掉再叫起來，只平剩下的。
- **重試的算法**：13:25 送一輪（還沒平的口數拆成每筆最多 10 口），沒平完就每分鐘再送一輪剩下的，
  最多重試 3 輪（13:26、13:27、13:28）。「委託沒有送出去」停下這一輪；只成交一部分照送下一筆。
  日盤 13:45 收盤（結算日是 13:30）之後不再送；13:45 之後才補跑就一張都不送，告警請人在夜盤處理。
- **平倉單 `FillUnknown`**：先把「這筆出場單不確定」寫進部位檔再查（查詢要 5 秒以上，期間被關掉的話
  重跑也不會再送），查到全部成交就記成出場、照送下一筆；只成交一部分、查不到、查詢失敗、沒有序號
  都不再送任何單（包括還沒送的那幾筆），告警附上券商紀錄的口數。查到的部分成交記進 `known_filled`。
- **查詢的三種結局**分開講：查到（`FillQuery.lots`）、查不到（`lots` None）、查詢失敗（`failure`）。
  `M999`、價差列、超過委託量、0 口、價格讀不出來都算「查詢失敗」，不算「查不到」。
- 大台、小台與「部位不確定」不看時間也不登入。不確定時大台、小台也告警，但不叫人自己平（會和券商
  13:30 的強平撞在一起），只請他 13:30 後確認帳戶。
- **自動下單關閉卻有微台部位檔**（今天進場後才關掉）：不登入、不送單，告警「部位還在」請人自己平。
- **登入失敗**不重試，立刻告警（還有時間讓人在 13:45 前自己平）。
- **13:20 進場截止之前被執行**（只會是手動）什麼都不做：盤中程式還在跑，下一筆成交會用它記憶體裡的
  部位整份覆寫部位檔，出場明細就不見了。
- **平倉成交了卻寫不進部位檔**：照樣把剩下的平完（記憶體裡的口數是對的），最後告警「部位檔沒記到
  出場程式這次的平倉」，請人**不要再執行出場程式**。
- 例行的平倉完成不發 Discord（規格：只有「有入場」與「需要你動手」才發）。
- **告警裡的期限**照出場程式自己停止送單的同一個期限：一般日 13:45 前請人自己平、之後請人在夜盤平；
  結算日 13:30 前請人在 13:30 前平、之後告知由交易所以最後結算價了結並請人結算後確認。部位檔讀不懂、
  出場程式當掉時不知道是不是結算日，兩種期限都講。期限前的「部位還在」與「意外中止」也叫人**自己平掉
  之後不要再執行出場程式**（部位檔沒有「已交給人處理」的記號，重跑會照檔再平一次）。
- **設定檔有錯**（盤中改設定打錯字、YAML 壞掉、`.env` 缺值）：不登入、不送單，其餘照常讀部位檔；
  有微台就告警「部位還在」並寫出設定錯在哪，`main()` 回 1。Discord 開關本身讀得到而且是 false 才不發。
- `main()` 只有程式本身出錯或設定有錯時回 1（並盡量發告警）；告警過的結局也回 0。
  **給 ticket 10：出場程式的排程不要設失敗重跑**——告警後使用者可能已經自己平掉剩下的口數，
  重跑就會再平一次，開出反向新倉。
